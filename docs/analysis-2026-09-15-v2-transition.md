대상: `docs/build-plan-v1.md` → `docs/build-plan-v2.md`, 현재 코드(수집기 3모듈), 문서·설정, 지도교수 피드백 2건.
근거는 file:line 과 명령 출력. 외부 사실은 공식 문서·원 논문 URL 을 붙였다. 확인 못 한 것은 "확인 필요".

## 0. 결론

1. **코드는 그대로 간다.** 수집기 3모듈(orderbook / binance_rest / writer, 소스 248줄)은 v2 에서도 1단계 그대로다. 테스트 18개 통과(0.11초). 지금 있는 코드 중 버릴 것은 없다.
2. **문서·설정은 v1 에 남아 있다.** CLAUDE.md:3 이 삭제된 `docs/build-plan.md` 를 `@` 임포트해서 세션마다 계획이 안 붙는다. README 12줄, CLAUDE.md 9줄, pyproject 1줄이 v1 서술이거나 없는 파일·명령을 가리킨다. 첫 PR 은 이것.
3. **v2 4절 축 정의 4개가 지금 문구로는 실험이 안 된다.** 시간 축의 "이벤트 단위" 는 이미 100ms 배치라 "100ms" 와 같은 점이다. 깊이 축의 "전체" 는 스냅샷 한도에 묶여 정의가 없다. 수량 축 "소수 2자리" 는 BTCUSDT 레벨의 43% 를 0(=삭제) 으로 만든다. 라벨은 임계값·horizon 단위·어느 데이터에서 만드는지가 없다. 이 넷은 10월 코드 전에 문서에서 정해야 한다.
4. **일정은 빠듯하다.** 9월 완료 조건 "72시간 무중단" 을 9월 안에 끝내려면 9/27 까지 코드가 돼야 한다. 남은 개발 시간은 주 10~15시간 × 1.7주 = 17~26시간, 미완 항목은 1절 에 10개. 교수 피드백대로 BTCUSDT 한 종목으로 줄이면 맞출 수 있다.
5. **교수 질문 "호가 데이터 오차 검증"** 은 5.2절 에 층위별로 정리했다. 한 줄 답: 순번 사슬은 "빠짐" 만 잡고 적용 로직 버그는 못 잡으므로, 거래소가 따로 주는 독립 채널과 대조해야 한다. 그중 **`@depth20@100ms` 가 결정적**이다. 오늘 45초 실측에서 그 `lastUpdateId` 가 델타 이벤트의 `u` 와 455/455 정확히 일치해, 100ms 마다 재구성한 상위 20레벨을 거래소가 보낸 값과 문자열 단위로 비교할 수 있다(452회 비교, 불일치 0). 하루 86만 회 대조가 대역폭 13KB/s 로 생긴다. 논문엔 "오차 없음" 이 아니라 측정한 불일치율과 커버리지를 싣는다.

## 5. 지도교수 피드백 반영

### 5.1 한 종목부터 (BTCUSDT)

바뀌는 것:

- v2:45 "수집 8~10종목" → "9~10월은 BTCUSDT 1종목, 첫 결과 후 확대". 수집기 설정은 종목 목록(길이 1)로 두어 늘릴 때 재작업이 없게 한다.
- 72시간 무중단도 1종목으로 한다. REST weight 는 재동기화 1회 250, 6000/분 한도 대비 무시할 수준. C-3·C-12(전 종목 동시 gap)는 확대 시점 항목으로 미룬다.
- 10월 첫 결과 = BTCUSDT, 깊이 10 vs 20(또는 5). "전체" 는 D-2 대로 Q1 전용이라 첫 비교에서 뺀다. 모델 수정(D-9)이 필요 없는 조합을 고르면 10월 부담이 준다.

### 5.2 호가 데이터에 오차가 없는지 검증하는 방법

먼저 답의 형태부터. **"오차가 없다" 는 증명할 수 없고, 증명해야 할 것도 아니다.** 바이낸스 현물 `@depth` 는 호가창 체크섬을 싣지 않고(Kraken·OKX 는 상위 레벨 체크섬을 보낸다, 확인 필요), 델타는 바뀐 레벨의 절대값만 실어 "안 바뀐 나머지" 에 대한 중복 정보가 없다. 그래서 답은 **"어떤 종류의 오차를 어떤 방법으로 얼마나 잡았고, 남은 불일치율이 얼마인지"** 다. 층위 4개로 나눠 설명하고, 각 층이 무엇을 못 잡는지를 같이 말하는 것이 핵심이다.

#### 층 1. 내부 일관성 — "빠짐없이 받았다"

U/u 순번 사슬(`U == 직전 u + 1`), 중복(`u ≤ 직전 u`), 스냅샷 직후 첫 이벤트 조건(`U ≤ lastUpdateId+1 ≤ u`). 이미 orderbook.py:46-55 에 있다.

- 잡는 것: 전송 손실, 재연결 겹침, 이벤트 순서 뒤집힘, 종목 라우팅 오류.
- **못 잡는 것: 적용 로직 버그.** 예를 들어 `_apply_levels` 가 메시지의 마지막 레벨을 빠뜨리는 off-by-one 은 순번 사슬·교차 검사·형식 검사를 전부 통과한다. 이것이 교수 질문의 핵심이고, 층 3 이 필요한 이유다.
- 지표: `gap_count`, `lost_updates = Σ(U_next − last_u − 1)`, 재동기화 횟수.

#### 층 2. 불변식 — "형태가 맞다"

최우선 매수 < 최우선 매도(교차 금지), 수량 > 0, 가격이 tickSize 배수·수량이 stepSize 배수, 소수 8자리 형식, E 단조 증가·간격 ≈100ms, rx−E 지연 분포로 시계 드리프트 감지.

- 매칭 엔진은 교차 호가창을 남기지 않으므로 **로컬 교차는 100% 우리 쪽 오류**다. 매수/매도를 바꿔 적용하는 실수는 첫 이벤트에서 바로 잡힌다.
- 안 만들어야 할 검사 두 개: "없는 레벨을 0으로 삭제" 는 정상이다(픽스처 601 이벤트에 1,853건, 100ms 창 안에서 생겼다 취소된 주문). "레벨 수 ≤ u−U+1" 도 정상 위반이 난다(602 중 3건, 체결 하나가 여러 레벨을 쓸어도 ID 는 하나). 둘 다 오류로 잡으면 오탐만 쏟아진다.

#### 층 3. 같은 거래소의 독립 채널과 대조 — "내용이 맞다"

**이것이 v1:31 이 말한 "유일한 독립 검증" 이고, 교수 질문의 실질적 답이다.** 델타 재구성과 무관하게 바이낸스가 따로 주는 상태와 비교한다. 2026-09-15 BTCUSDT 45초 실측으로 세 채널을 모두 검증했다.

| 체결 `@trade` | 체결가 vs 직전 배치 최우선 호가 | 1,586건 중 위반 7건(0.4%) | 4.7 KB/s |

읽는 법 세 가지:

1. **`@depth20@100ms` 가 가장 좋은 참조다.** 문서에는 "같은 순번 공간" 이라는 말이 없는데, 실측에서 `lastUpdateId` 가 델타 이벤트의 `u` 와 **정확히** 일치했다(455/455, 나머지 1건은 캡처 종료 경계). 즉 100ms 배치마다 재구성한 상위 20레벨을 바이낸스가 보낸 상위 20레벨과 **문자열 단위로 비교**할 수 있다. 하루 864,000회 비교가 공짜로 생긴다. REST 폴링(몇 분에 한 번)보다 4자리수 촘촘하다.
2. **REST 스냅샷의 정렬 함정은 실제로는 덜 심각했다.** 문서(5단계)는 `lastUpdateId` 가 첫 이벤트의 `[U;u]` 안 어디든 올 수 있다고 전제하지만, 실측 16/16 이 배치 끝 `u` 에 정확히 떨어졌다(배치 폭 5~52, 우연일 확률 ≈1e-8). 스냅샷 메모리가 100ms 배치 경계에서 갱신되는 것으로 보인다(문서에 없음, 일반화 주의). 그래도 규칙은 못 박아야 한다: **`u == L` 인 메시지가 있을 때만 정확 비교하고, 아니면 그 스냅샷을 버린다.** 실측대로면 버리는 일이 거의 없다.
3. **체결 대조는 참조로 쓰지 마라.** 1,586건 중 7건(0.4%)이 "매도 체결가 > 직전 최우선 매수가" 로 나왔고, 31건은 체결 레벨이 직전 호가창에 없었다. 100ms 배치와 체결 시각의 정렬 오차 때문이며 우리 오류가 아니다. 공식 문서에 체결–호가 정렬 규정이 없으므로(확인함) 논문에는 "자체 정의 일관성 검사" 로만 쓰고 허용 오차를 명시한다.

비교 **범위**도 정해야 한다. 스냅샷 한도 밖은 비교할 수 없다. 실측한 레벨별 가격 거리(BTCUSDT):

| 레벨 순위 | 매수 쪽 거리 | 매도 쪽 거리 |
|---|---|---|
| 5 | 0.09 USDT | 0.84 USDT |
| 20 | 3.17 | 4.71 |
| 100 | 20.67 | 13.19 |
| 1000 | 142.42 | 273.15 |
| 5000 | 698.04 | 993.05 |

모델 입력(상위 10~20)은 mid 대비 0.01% 안이라 어떤 참조로도 덮인다. "전체" 깊이(D-2)만 참조가 없다.

#### 층 4. 파이프라인 무결성 — "저장하고 복원해도 같다"

- **파일 매니페스트**(v2:36): 파일마다 원문 sha256, `.zst` sha256, 바이트 수, 줄 수, 첫/끝 줄의 rx·E·U·u, 그 시간대 gap/dup 수, 스키마 버전, 수집기 git sha.
- **파일 경계 연속성**: 파일 H 의 마지막 `u + 1 == 파일 H+1 의 첫 U`. 파트 파일(`.1.zst`)은 이름이 아니라 첫 줄 rx 로 정렬(C-9).
- **재생 결정성**: 라이브에서 60초마다 호가창 상위 K 레벨의 sha256 을 `HH.bookhash.ndjson` 에 남기고, 원본 파일을 재생해 같은 `u` 에서 같은 해시가 나오는지 본다. 저장·복원 경로 전체(줄 유실, 중복, 순서, zstd 손상, 래퍼 벗기기, 스냅샷 정렬)를 한 번에 덮는다. 단 라이브와 재생이 같은 `OrderBook` 을 쓰므로 **적용 로직 버그는 양쪽에서 똑같이 재현되어 해시가 일치한다.**
- **차등 재생**: 그래서 복원기(3절)를 orderbook.py 를 보지 말고 문서만 보고 다른 자료구조(tickSize 정수 인덱스 + numpy)로 새로 쓴다. 두 구현이 같은 파일에서 같은 체크포인트 해시를 내면 적용 로직 버그가 걸러진다. 어차피 D-2·C-10 때문에 복원기는 numpy 로 다시 써야 하므로 추가 비용이 거의 없다. 논문에 "두 독립 구현 일치율 100%" 로 쓸 수 있다.
- **두 수집기 병렬**: 72시간 테스트 동안 두 번째 컨테이너를 같은 종목으로 돌려 `u` 로 조인한다. 한쪽에만 있는 gap 은 로컬 문제, 양쪽 같은 위치면 상류 문제. 실측에서 두 REST 호스트(api.binance.com, data-api.binance.vision)가 같은 `lastUpdateId` 를 준 7쌍은 **본문 바이트까지 동일**했다.

#### 72시간 무중단 전에 켤 최소 집합

구현 시간 합이 하루를 넘지 않는다. 이게 없으면 첫 72시간 데이터에 품질 수치가 없다.

1. `@depth20@100ms` 를 같이 구독해 상위 20레벨 대조(층 3-1). 하루 864k 회 비교가 공짜.
2. 교차 검사 + 형식 검사 카운터(층 2).
3. gap/dup/재동기화 카운터와 로그(층 1, v2:32·35).
4. 라이브 체크포인트 해시 기록(층 4). **기록이 없으면 지난 72시간을 나중에 이 방법으로 검증할 수 없다.**
5. zstd 체크섬 켜기(C-16) + 파일 매니페스트(v2:36).
6. REST 주기 스냅샷 저장(층 3-2). 몇 분에 한 번이면 weight 부담이 없다.

#### 논문에 실을 수치

"오차 없음" 대신 아래를 표로 싣는다. 분모·분자를 반드시 같이 적는다.

| 지표 | 정의 |
|---|---|
| 커버리지 | 갭 없는 시간 / 전체 수집 시간 |
| 갭·재동기화 | 72시간당 gap 건수, 놓친 업데이트 ID 수, 재동기화 횟수 |
| 부분 호가 대조 불일치율 | 불일치 레벨 수 / 비교한 레벨 수 (`@depth20` 정렬 비교) |
| REST 스냅샷 불일치율 | 같은 정의, 상위 N 과 전체를 따로 |
| 상위 10레벨 불일치율 | 모델 입력에 실제로 영향을 주는 범위만 |
| 신뢰 구간 밖 시간 비율 | 최우선 호가가 스냅샷 가격 범위를 벗어난 시간 비율 |

목표값은 0 이 아니라 "측정해서 보고" 다. 참고로 상용 수집 서비스(Tardis.dev)가 공개하는 완전성은 약 99.9%(좋은 날 99.99%) 이고, 같은 절차(REST 1000레벨 + `@depth@100ms` + U/u 검증)를 쓴다. 우리가 그 수준을 재현했다고 보이면 충분하다.
