### MEMO

- `@depth` 메시지 하나는 "이 가격 레벨의 새 합계 수량"의 목록이지 호가창 상태가 아님 → 시작점이 될 전체 상태를 REST 스냅샷으로 받아야 함
- 예: 50,000에 2 BTC 대기 중, 누가 0.5 BTC를 추가로 걸면 메시지는 `매수 50,000 → 2.5` (요청 응답이 아니라 push, 증분이 아니라 절대값)
- 폴링 이유 세 가지: 갭 복구, 드리프트 검증, 체크포인트 참조
- 정합성 검사가 유일한 독립 검증. 갭 없이 받아도 파서 버그로 틀어질 수 있고, 불일치율 0.0X%가 논문의 데이터 품질 수치가 됨
- `U`/`u`: 메시지 하나가 100ms 동안의 변경을 묶어 보내므로 `U`는 첫 순번, `u`는 마지막 순번. 정상이면 다음 `U` == 직전 `u + 1`

```
메시지 1: U=157, u=160   (157~160번 변경 4개)
메시지 2: U=161, u=161   → 160+1 = 161, 정상
메시지 3: U=162, u=165   → 161+1 = 162, 정상
메시지 4: U=170, u=172   → 165+1 = 166인데 170이 옴 → 166~169번 4개를 놓침 = 갭
```

- 중복은 스냅샷 재동기화 직후와 겹치기 재연결 순간에 발생. 수량이 절대값이라 옛 메시지를 다시 적용하면 호가창이 되돌아가므로 반드시 걸러야 함
- 틱 사이즈 이력이 필요한 이유: 거래소가 단위를 바꾸면 그 날짜의 단위로 나눠야 정수화가 무손실로 유지됨
